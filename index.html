What the form code is actually doing

<tag> content </tag>

Most elements have an opening tag, content, and a closing tag. Nesting elements puts one piece inside another.

<form>

A form is a package of information. Pressing its submit button sends every named input in that package.

for="username"

A label’s for must match an input’s id. That connection helps screen readers and lets a user click the label.

name="username"

The name becomes the key sent to the server. Without a name, the typed value is not included in the form data.

type="text"

The input type changes the control and its rules. The video demonstrates text, password, email, number, radio, checkbox, and more.

required

This is a Boolean attribute: simply including it tells the browser not to submit an empty field.

A MENTAL MODEL FOR EVERY FUNCTION

A function is a small machine with a clear job

Before writing a function, describe its contract: what data enters, what data it produces, and what it changes outside itself. A name in the definition’s parentheses is a parameter—an empty input slot. The real value supplied when the function is called is an argument. The value after return is the output.

Inputdata entering → Functionone named job → Outputdata returned
A function may also cause a side effect It changes something outside its own local work: memory, a file, a database, the browser, or the terminal.

Not every function has all three. A page-building function can return HTML without changing anything. A save function may change a database and return no useful data. A Flask route often does both: it changes stored data and returns a response.

ONE IMPORTANT ARCHITECTURE CHOICE

Why does our server return the whole HTML page?

We are building a server-rendered app. The browser asks for /, Python combines the current task data with the page structure, and the server returns one finished HTML document. After a form changes the data, the redirect makes the browser request and display a fresh page.

THE STYLE WE USE

Server-rendered

GET / → Python reads data → Python produces complete HTML → the browser displays it.

In this raw server, make_page builds that HTML string. In Flask, the same job moves into templates/index.html, and render_template fills it with data. The browser still receives complete HTML.

ANOTHER COMMON STYLE

API-style

The browser first loads HTML plus JavaScript. That JavaScript asks an API address such as /api/items for data. The server usually replies with JSON data such as {"text": "Pack lunch", "done": true}, not a finished page.

The JavaScript must then turn that data into visible HTML and update the page.

Both styles are normal. Plain HTML cannot fetch JSON and turn it into changing task rows by itself; an API-style version would require JavaScript as a third programming language. This course uses server rendering so you can understand a complete app with Python and HTML first.

UNDERSTAND THE VIDEO

How a browser and server have a conversation

socket

A socket is one end of a network connection. The video creates one, attaches it to a port, listens, and accepts a browser connection.

bytes ↔ text

Networks move bytes. decode() turns incoming bytes into readable text; encode() turns a response back into bytes.

GET / HTTP/1.1

The request’s first line contains a method, a path, and an HTTP version. GET means “send me something.”

POST

POST means “here is information that should change something.” Our forms use it to add, check, or delete.

200 OK

A response starts with a status line. 200 means the request worked. Headers describe the response; the body contains the HTML.

303 See Other

After a POST, we send the browser back to /. This prevents refreshing the page from submitting the form twice.

VIDEO STARTER · server.py
import socket

SERVER_HOST = "127.0.0.1"
SERVER_PORT = 8080

server_socket = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
server_socket.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
server_socket.bind((SERVER_HOST, SERVER_PORT))
server_socket.listen(5)

print(f"Listening on port {SERVER_PORT}...")

while True:
    client_socket, client_address = server_socket.accept()
    request = client_socket.recv(1500).decode()
    print(request)

    request_line = request.splitlines()[0]
    method, path, version = request_line.split()

    if method == "GET" and path == "/":
        with open("index.html", encoding="utf-8") as file:
            content = file.read()
        response = "HTTP/1.1 200 OK\r\nContent-Type: text/html\r\n\r\n" + content
    else:
        response = "HTTP/1.1 404 Not Found\r\n\r\nPage not found"

    client_socket.sendall(response.encode())
    client_socket.close()

WHY CHANGE IT?

The raw server taught the lesson—but it is hard to grow

Your current file manually reads form bytes, splits URLs, chooses status codes, builds HTML inside Python strings, and repeats redirect headers. Every new button adds more parsing. Flask already solves that plumbing, so our code can say what the app means: “this URL adds a task” or “render this HTML template.” The browser still sends the same HTTP requests you learned in Lesson 2.

UNDERSTAND THE VIDEO

What Flask adds—and what it does not

app = Flask(__name__)

This creates the application object. Flask uses __name__ to locate files belonging to this project.

@app.route("/")

A decorator connects a URL path to the function immediately below it. Flask calls that function when a matching request arrives. That function is called a view.

return

The view’s output becomes the HTTP response. It can be plain text, rendered HTML, or a redirect. Returning also ends that run of the function.

render_template()

This opens a file from templates/ and fills in its Jinja placeholders before sending the HTML.

request.form

Flask parses an incoming form body for us. request.form["text"] reads the input whose HTML name is text.

<int:item_id>

This part of a route accepts a number from the URL. Flask converts it to an integer and supplies it to the view’s matching item_id parameter.

redirect() + url_for()

url_for finds the URL connected to a function name. redirect turns that URL into a response telling the browser where to go next.

debug=True

During learning, Flask automatically reloads after code changes and shows useful errors. Never use debug mode on a public production server.

Start app.py with the video’s Flask app

VIDEO STARTER · app.py
from flask import Flask

app = Flask(__name__)


@app.route("/")
def home():
    return "<h1>Hello from Flask!</h1>"


@app.route("/about")
def about():
    return "This is the about page."


if __name__ == "__main__":
    app.run(debug=True)

After creating app.py, run it once and visit localhost:5000, then localhost:5000/about. The path changes which function runs. Read the functions as contracts: home and about go below their decorators and above app.run; neither takes a parameter or has a side effect; each returns a response string.

The last missing piece is memory that survives a restart. SQLite stores it in one file.

This lesson adds Permanent lists and tasks that survive server restarts.

WHY CHANGE IT?

A useful app must remember tomorrow

Right now, the lists exist only while Python is running. A database writes structured rows to long-term storage. SQLite is a good first database because Python already includes it, it needs no account or separate database server, and the whole database is one local file. Flask will keep handling the web requests; SQLite will take over the job of remembering.

UNDERSTAND THE VIDEO

Translate database words into ordinary actions

connection

sqlite3.connect("todo.db") opens the file—or creates it the first time. The connection is our path into the database.

table / row / column

A table is like a spreadsheet. Every row is one thing; columns describe it. One item row has an ID, list ID, text, and done value.

CREATE TABLE

Define the columns and rules. IF NOT EXISTS makes it safe to run setup every time the app starts.

INSERT / SELECT

INSERT writes a row. SELECT reads matching rows back. fetchall() turns the result into something Python can loop over.

UPDATE / DELETE

UPDATE changes existing rows; DELETE removes them. A WHERE clause chooses exactly which rows are affected.

commit()

A change is not permanent until it is committed. Think of this as pressing Save after INSERT, UPDATE, or DELETE.

?

Question marks are safe value placeholders. Keep user text separate from SQL instead of building one SQL string.

foreign key

items.list_id points to lists.id. This is how each task remembers which list owns it.

VIDEO STARTER · use individual patterns in app.py
import sqlite3

connection = sqlite3.connect("employee.db")
cursor = connection.cursor()

cursor.execute("""
    CREATE TABLE IF NOT EXISTS employees (
        first TEXT,
        last TEXT,
        pay INTEGER
    )
""")

cursor.execute(
    "INSERT INTO employees VALUES (?, ?, ?)",
    ("Ada", "Lovelace", 50000),
)
connection.commit()

cursor.execute(
    "SELECT * FROM employees WHERE last = ?",
    ("Lovelace",),
)
print(cursor.fetchall())

connection.close()

4.1

Exercise: replace temporary memory

Keep your routes and template, but change where each route reads and writes data.

i
Where the new functions go

Keep the Flask app creation at the top. Put the database filename below it, then get_db, then init_db, then the six route functions. Keep the video’s if __name__ == "__main__" section at the very bottom.

get_db(database_path)

Put it
Below the database filename and above init_db.
Input
database_path: the filename string for the database.
Output
An open SQLite connection object.
Side effect
Opens the file, or creates it if it does not exist.

init_db(connection)

Put it
Directly below get_db and above the first route.
Input
connection: the open connection returned by get_db.
Output
Nothing useful; reaching the end returns None.
Side effect
Creates missing tables and commits those changes to the file.
↻
The six route contracts mostly stay the same

Their placement, inputs, and redirect or page outputs stay as described in Lesson 3. Their side effects move from changing a Python list in RAM to changing rows in SQLite. The home route now reads rows from SQLite instead of reading the old lists variable.

  1. Open the same app.py you finished in Lesson 3. Do not create a new file. Add the video example’s sqlite3 import at the top with the other imports.
  2. On the first line below the Flask app creation, create a variable that stores the database filename todo.db.
  3. Below that variable, define get_db with one parameter named database_path. Inside it, pass that parameter to sqlite3.connect and return the resulting connection. Do not close it inside this function; its caller still needs to use the output.
  4. Below get_db, define init_db with one parameter named connection. Inside it, adapt the video’s CREATE TABLE operation to make a lists table with an automatic integer ID and required name.
  5. Still inside init_db, create an items table. Give it an automatic integer ID, a required list_id, required text, and a done number that defaults to zero. Make list_id a foreign key pointing to the lists table. Commit before the function ends.
  6. At the bottom of the file, find the existing if __name__ == "__main__" section. Before its app.run line, call get_db with the database filename, pass the returned connection into init_db, and then close that connection. Run the app once and confirm that todo.db appears beside app.py. Stop the app before continuing.
  7. Delete the old starter lists variable and both next-ID counters. SQLite will create IDs and remember rows now.
  8. At the start of index, pass the database filename into get_db and store its returned connection. SELECT all list rows ordered by ID. For each list row, SELECT only the items whose list_id matches, also ordered by ID. Build the nested data your template expects, close the connection, and return the rendered page. Its output is still HTML; its external interaction is now reading the database.
  9. At the start of add_list, pass the database filename into get_db and store its returned connection. Replace the Python-list append with an INSERT into the lists table, using a question-mark placeholder for the submitted name. Commit, close, and return the same redirect as before.
  10. In delete_list, get and store a connection the same way. First DELETE every item whose list_id matches the input. Then DELETE the matching list row. Doing both explicitly avoids relying on automatic cascade settings. Commit, close, and return the redirect.
  11. In add_item, get and store a connection. INSERT the list_id input, submitted text, and unfinished done value. Commit, close, and return the redirect.
  12. In toggle_item, get and store a connection. SELECT the current done value for the item_id input. UPDATE that row to zero if it was one, or one if it was zero. Commit, close, and return the redirect.
  13. In delete_item, get and store a connection. DELETE the row matching the item_id input. Commit, close, and return the redirect.
✓
Database checkpoint

Search app.py for every place that used to append, remove, or change a Python list. Each of those actions should now use INSERT, DELETE, or UPDATE. The home route should use SELECT.

?
Why are there question marks in the SQL?

They are safe placeholders. Python puts the values into them without treating a task’s text as SQL code. Always use placeholders for user input.

4.2

Test long-term memory

Make data, restart Python, and make sure the data stays.

  1. Run python app.py again and open http://localhost:5000.
  2. Create a list named Test persistence.
  3. Add an item named This should stay and check it.
  4. Stop the server with Ctrl + C. Start it again with python app.py.
  5. Refresh the browser. Your list and checked item should still be there.

A new file named todo.db appears automatically. Do not open or edit it like a text file.

FINAL CHALLENGE

Test every path

Create two lists. Put two items in each. Check one item. Delete a different item. Delete one entire list. Restart the server and confirm the remaining list is unchanged. The test names are entirely your choice; only the behavior matters.

If something goes wrong
  • Read the last line of the terminal error first.
  • Check that indentation uses four spaces inside each function.
  • Check that every quote, bracket, and parenthesis has a matching partner.
  • If you changed the database table code, stop the server, delete only todo.db, and restart. This erases your test data and rebuilds the tables.
